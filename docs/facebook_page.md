# GeoCharge Facebook page: scheduled posts

The page's posting queue is filled by `tools/fb-queue.mjs`. It reads the built
articles under `site/blog/`, picks what should go out next, and hands Facebook a
batch of posts with a publish time attached. **Facebook does the waiting**, so
nothing needs to be running on any machine when a post actually goes live.

One run a month is both the intended cadence and roughly the maximum: Facebook
will not accept a publish time more than about 30 days out, so a single run can
only ever fill about a month of slots. See the horizon note below.

## Slots

Tuesday 19:00 and Saturday 12:00, Tbilisi time, defined in `SLOTS` at the top of
the script. Asia/Tbilisi is UTC+4 all year with no DST, so the offset is hard
coded and stays correct.

## What gets posted

- Metadata (title, description, canonical URL, og image) is parsed out of the
  **built** page, so a post can never link to a page that is not live.
- The hook text is authored in the `HOOKS` map, two variants per article, so a
  second pass through the back catalogue does not repeat itself word for word.
  An article with no entry falls back to its meta description.
- `ORDER` is the first pass through the catalogue, mixed by topic. After
  everything has gone out once, least recently posted wins and `ORDER` only
  breaks ties. A brand new article is not in `ORDER`, which puts it first.
- `SEASON` holds articles back outside their months: the winter guide only in
  November to February, the two Turkey guides only in May to September.

`tools/fb-state.json` records what was queued and when. It is committed, it
holds no secrets, and deleting it makes the rotation start over.

## Getting the token

The token itself has to be generated by hand, signed in as a page admin.

1. Open the [Graph API Explorer](https://developers.facebook.com/tools/explorer/?app_id=2245805416179108)
   with the GeoCharge app selected.
2. Under Permissions add `pages_manage_posts`, `pages_read_engagement` and
   `pages_show_list`.
3. **User or Page → Get Page Access Token**, then **Generate Access Token**.
   Approve the dialog and pick the GeoCharge page.
4. That token expires in about an hour. Exchange it for a permanent one:

```bash
curl "https://graph.facebook.com/v26.0/oauth/access_token?grant_type=fb_exchange_token&client_id=APP_ID&client_secret=APP_SECRET&fb_exchange_token=SHORT_TOKEN"
```

   The App Secret is under **App settings → Basic**. Or skip the curl and use
   the [Access Token Debugger](https://developers.facebook.com/tools/debug/accesstoken/),
   which has an **Extend Access Token** button at the bottom that does the same
   exchange without handling the secret by hand.
5. With that long lived **user** token, ask for the page token **directly**:

```
1227753007083449?fields=id,name,access_token
```

   **Do not use `/me/accounts` here.** For this page it returns `{"data": []}`
   even with `pages_show_list` granted and the page selected in the login
   dialog, because the page is owned by the GeoCharge business portfolio rather
   than linked to the personal profile the classic way. Querying the page node
   by id works and returns the same token. Confirmed 2026-08-19.

   A page token derived from a long lived user token does not expire; the
   Access Token Debugger reports `expires_at: 0` for it.
6. Write both into `.env` at the repo root, which is gitignored:

```
FB_PAGE_ID=...
FB_PAGE_TOKEN=...
```

Nothing else reads that file, and it must never be committed. Confirm the token
is the permanent one by pasting it into the Access Token Debugger: Expires
should read **Never**.

## Running it

Preview the next eight posts. Writes `marketing/fb-queue.md` and changes nothing
on Facebook. This is the default: publishing needs an explicit flag.

```bash
node tools/fb-queue.mjs --count 8
```

Send that batch to Facebook's scheduled queue:

```bash
node tools/fb-queue.mjs --count 8 --publish
```

See what is already queued:

```bash
node tools/fb-queue.mjs --list
```

Drop one scheduled post, by the id shown in `--list`:

```bash
node tools/fb-queue.mjs --cancel POST_ID
```

Cover the whole catalogue once, sizing the batch automatically to whatever has
never been posted:

```bash
node tools/fb-queue.mjs --all
```

`--all` overrides `--count`. It also relaxes `SEASON`: an out-of-season article
is moved to the back of the run rather than dropped, so a full sweep really does
include everything. That is a deliberate trade, and it means a sweep started in
summer puts the winter guide on its last slot, which may still be autumn.

`--start YYYY-MM-DD` moves the first slot, useful when a batch is being planned
ahead of time.

## Checking a token before trusting it

A page token can look fine and still be missing the one permission that matters.
Paste both tokens into the Access Token Debugger, or run this in the Explorer
with the **user** token selected:

```
debug_token?input_token=THE_PAGE_TOKEN
```

What a working token looks like:

- `type: PAGE`
- `profile_id: 1227753007083449`
- `expires_at: 0`, meaning it never expires
- `scopes` **includes `pages_manage_posts`**

The failure seen during setup was a token that was valid, permanent and scoped
to the right page, but whose scopes were only `pages_show_list`,
`pages_read_engagement` and `public_profile`. Reads worked, scheduling would
have failed. `pages_manage_posts` has to be ticked in the login dialog itself;
adding it to the app's use case is necessary but not sufficient.

## Notes

- **The scheduling horizon is about 30 days, not the six months the Pages API
  docs claim.** Measured on 2026-08-19: 27 days ahead was accepted, 31 days
  ahead came back as a bare `(#100) The specified scheduled publish time is
  invalid`. `HORIZON_DAYS` is set to 29 for margin, and `slots()` stops there,
  so a batch is trimmed with a message instead of dying mid-run against the API.
- Facebook also rejects anything less than 10 minutes ahead. The script skips
  that window on its own.
- Slots already used by an earlier run are read out of the state file and
  skipped, so a second run inside the same month tops up the queue rather than
  double booking times that are already filled.
- The Graph API version is pinned to `v26.0`, the current version in the console
  as of August 2026, and is overridable with
  `FB_API_VERSION`. Versions retire roughly two years after release, so a hard
  failure mentioning an unknown version means it is time to bump it.
- The state file is rewritten after **every** post, not at the end, so a batch
  that dies halfway cannot cause the next run to queue the same articles again.
- Scheduling a batch is publishing to a public page. Preview it, approve it,
  then run `--publish`.
- **The figures inside `HOOKS` are frozen prose, unlike the articles, whose
  numbers are injected from the live gist at build time.** A hook that quotes a
  station count or a tariff will drift away from the article it links to. Reread
  the hooks against the built page whenever the catalogue moves noticeably, and
  keep new hooks qualitative where a number is not the point.
